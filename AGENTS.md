# Working guide for DotCommands

## Purpose and scope

This repository is a home for small ZX Spectrum Next dot commands that run
under NextZXOS. New commands may be written in Z80/Z80N assembly or in C with
Z88DK. Keep work self-contained in this repository unless the user explicitly
asks for integration with another project.

The repository is CC0-1.0 licensed. The canonical remote is
`https://github.com/weareroad/DotCommands` and the default branch is `main`.

## Read this first

Start each task by reading this file, `README.md`, the relevant source, and
`git status`. Preserve unrelated user changes.

The current checkout is a small, transitional project:

- `src/cdn.asm` is the SJAsmPlus source for `.CDN`.
- `src/set32.asm`, `src/set64.asm`, and `src/set85.asm` are SJAsmPlus ports of
  the original NextForge/ZNC sources.
- `dot/set32`, `dot/set64`, and `dot/set85` are checked-in, extensionless
  command binaries.
- `dot/cdn` is the checked-in `.CDN` binary generated by `build.ps1`.
- `docs/dot-*.md` contains the detailed user and implementation guide for
  each command or closely related command family. Keep this prefix convention
  when adding command documentation.
- The optimized mechanical SJAsmPlus `SetNN` ports were 37 bytes and
  byte-identical to their tested NextForge/ZNC artifacts. The current
  help-enabled binaries are 145 bytes. Their pre-rebase help behavior was
  tested in CSpect; the merged optimized core requires a final regression.
- `.CDN` is 4488 bytes. Exact changes, LFN expansion, interactive selection,
  cancellation, and the nine-choice truncation limit have been tested in
  CSpect.
- `build.ps1` is the reproducible SJAsmPlus entry point for every current
  command and can verify the SetNN binaries against their reference hashes.
- `.tools/` is ignored and is suitable for a project-local toolchain.

The README contains valuable NextZXOS ABI research, but parts of it describe
an older, larger SJAsmPlus implementation that was removed in commit
`c27830b`. In particular, the compact current sources do not contain all the
paging, `ERR_NR`, and diagnostic handling described there. Treat current
source and binaries as authoritative for current behaviour; treat the README
as design history where it differs. When implementation work settles, update
the README so it describes the code that actually ships.

## Current commands

`.CDN` changes directory with esxDOS-compatible `F_CHDIR` (`$A9`). It obtains
the canonical, drive-qualified path using `F_GETCWD` (`$A8`), then expands any
8.3 aliases by matching each component against the paired LFN/SFN entries from
`F_OPENDIR` (`$A3`) mode `$18` and `F_READDIR` (`$A4`). Mode `$18` requires
NextZXOS 2.07 or later. With no argument it only prints the expanded current
path. If an exact change fails, it offers up to nine child-directory LFNs that
start with the argument; digits select, ENTER selects the first, and other keys
cancel. After displaying choices it prints a blank line and restates the final
path, including the unchanged path after cancellation. It accepts quoted LFNs
and returns native esxDOS errors. Exact `-h`, `-H`, and `-?` arguments print
brief built-in help. Its source is standard SJAsmPlus syntax.

The compact `SetNN` sources assemble at `$2000`, allocate token space plus a
40-byte calculator-stack reserve with the 48K ROM `BC_SPACES` routine, copy a
tokenised NextBASIC command into it, and call `IDE_BASIC` through `M_P3DOS`.
`IDE_BASIC` reclaims that workspace during execution.

They implement:

- `.SET32` - `SPECTRUM CHR$ %32 : CLS`
- `.SET64` - `SPECTRUM CHR$ %64 : CLS`
- `.SET85` - `SPECTRUM CHR$ %85 : CLS`

The token stream in each current source is the best record of the exact BASIC
form: `$A3,$C2,$25,"NN",$3A,$FB,$0D`.

Exact `-h`, `-H`, and `-?` arguments print `v0.1 - we.are.road`, a blank line,
and a mode-specific one-line description. Help must not change mode or clear
the screen. Other arguments retain the historical mode-setting behaviour.

## Dot-command constraints

Preserve these platform contracts unless the command deliberately uses a
different documented NextZXOS facility:

- A standard dot command is loaded into DivMMC RAM at `$2000` and its initial
  image must fit within 8 KiB.
- On entry, `HL` points to the argument text (or is zero when there are no
  arguments), and `BC` describes the full command line excluding the dot.
- Return with carry clear for success. For failure, follow the documented
  NextZXOS dot-command error convention and state which error code is used.
- Memory below `$4000` is not ordinary Spectrum RAM while a dot command runs.
  Do not pass pointers into the image at `$2000` to APIs requiring normal RAM.
- Allocate normal-RAM API buffers safely and reclaim every successful
  allocation. The existing code uses ROM `BC_SPACES` (`$0030`) and
  `RECLAIM_2` (`$19E8`).
- Do not move the machine stack outside the range required by a ROM or
  NextZXOS API.
- Preserve paging, interrupt state, index registers, alternate registers, and
  system variables whenever the invoked ABI requires it. Document intentional
  clobbers near the call site.
- `M_P3DOS` (`$94`) and `IDE_BASIC` (`$01C0`) have special paging and alternate
  register requirements. Re-read the API documentation and the README before
  changing those calls; do not infer success solely from an unverified flag.
- Tokenised BASIC is not plain ASCII. Verify token values and numeric encoding
  against NextBASIC and on a real command invocation.

## Assembly work

- Use Z80 instructions by default and Z80N instructions when they provide a
  clear benefit. Make the selected CPU explicit in the build configuration.
- Keep the runtime origin at `$2000`/`0x2000` and emit a raw, unpadded binary.
- Follow SJAsmPlus syntax consistently. The SetNN ports deliberately preserve
  the historical emitted bytes; use the reference verification before making
  behavioural changes so syntax or toolchain drift is caught explicitly.
- Prefer named constants for ROM calls, NextZXOS calls, ports, system
  variables, tokens, and error values.
- Comment ABI assumptions, entry/exit registers, memory ownership, paging,
  and non-obvious Z80N optimisations. Avoid comments that merely restate an
  instruction.
- Share implementation code when variants differ only by constants, but keep
  each shipped command easy to identify and build.

## Z88DK C work

- Use the Z88DK ZX Spectrum Next target and explicitly configure the output as
  a NextZXOS dot command/raw image at `$2000`. Do not assume a normal Spectrum
  program CRT is suitable.
- Keep startup code and runtime dependencies small. Inspect the linked map and
  final binary rather than assuming library calls fit within 8 KiB.
- Put ABI boundaries in small assembly shims when C cannot reliably express
  register placement, alternate register use, paging, or carry-flag returns.
- State the compiler library model and required Z88DK version in the checked-in
  build configuration. Avoid undocumented, machine-local compiler flags.
- Do not use heap, stdio, or broad runtime facilities casually; prefer small,
  explicit NextZXOS/esxDOS calls whose memory and register effects are known.

## Build and generated binaries

Run the canonical assembly build from the repository root with:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ./build.ps1 -Clean
```

The script uses SJAsmPlus, writes all release artifacts under `dot/`, and
enforces the 8 KiB limit. Pass `-Assembler path/to/sjasmplus` to select another
executable or `-Command cdn|setnn|set32|set64|set85` to select a subset. Run
`-Command setnn -VerifySetNNReference` to assemble temporary outputs, compare
their recorded SHA-256 hashes, and leave the normal release artifacts
untouched. Verification defines `REFERENCE_BASELINE`, which omits only the
help dispatcher and text so the optimized 37-byte core can still be checked.

When extending the build system:

1. Make it non-interactive and runnable from the repository root.
2. Pin or clearly document the assembler/compiler version and CPU target.
3. Put temporary outputs in an ignored directory.
4. Emit extensionless release files under `dot/`.
5. Fail if any dot command exceeds 8192 bytes.
6. Provide clean, build-all, and per-command targets.
7. Document the exact command in `README.md` and here.

Checked-in files under `dot/` are release artifacts for direct copying to an
SD card. Update them only when their sources change, verify their size, and
call out any source/binary mismatch. Do not add object files, listings, maps,
or local toolchains to Git unless the project deliberately adopts them.

## Verification

For every change, run all checks the repository supports and at minimum:

1. Run `git diff --check`.
2. Build every affected command with the declared toolchain, if available.
3. Confirm each release binary is non-empty and below 8192 bytes.
4. Compare binary size and bytes with the previous artifact; explain changes
   that are not an obvious consequence of the source edit.
5. Test from `C:/DOT/` under NextZXOS. Exercise no arguments, valid arguments,
   invalid arguments, repeated invocation, and failure paths as applicable.
6. Verify carry/error behaviour, prompt and cursor usability, preserved paging
   and stack state, and that an existing BASIC program is not damaged.
7. Test in an emulator where useful, but distinguish emulator testing from
   real Spectrum Next hardware testing.

If hardware or emulator testing was not possible, say so explicitly in the
handoff. Never describe assembly success alone as runtime verification.

## Change discipline

- Keep changes focused and avoid drive-by renames or formatting churn.
- Update documentation with new commands, invocation syntax, installation
  names, build instructions, ABI assumptions, and known hardware results.
- Do not silently discard useful historical findings. Preserve them as a
  clearly labelled note when they still affect future implementation choices.
- Never commit, push, publish a release, or modify the user's SD card unless
  the user explicitly asks.
